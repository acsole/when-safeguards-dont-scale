# Contributing to When Safeguards Don't Scale

Thanks for considering a contribution, including if this is your first-ever open-source contribution. This project is written to be approachable: if any of these instructions are unclear, that itself is worth an issue.

## Before you start

- Read the [README](README.md), especially the **"What this is NOT"** section, so your contribution fits the project's actual scope.
- Check open [issues](../../issues) and [pull requests](../../pulls) to avoid duplicate work.
- For anything non-trivial (a new section, a structural change to the case study or the working-method, a reframing of the analysis), please open an issue **before** writing, so we can align on the approach first.

## What this project is

This repository is a written case study on AI safeguards, plus the reusable AI working-method it was built with, its diagrams, work orders, and templates. It ships documents, not code: there is no application to run, no dependencies to install, and no dataset.

That shapes what a useful contribution looks like.

## Ways to contribute

- **Documentation fixes.** Typos, unclear passages, broken links, missing context in any of the documents. These are genuinely welcome and often the highest-value contributions here.
- **Translations.** The project is bilingual (Spanish content under `ES/`, English under `EN/`, which is still being filled in). Help translating between Spanish and English, and keeping both in sync, is especially valuable.
- **Factual and analytical review.** Flag a claim you think is wrong, overstated, or unsupported. The project's whole premise is honesty about what does and does not hold, so a well-argued challenge to the analysis is welcome.
- **Diagrams.** Improvements or corrections to the SVG figures under `diagrams/`.
- **Templates and work orders.** Fixes or improvements to the reusable materials.

## How to work on a change

1. Fork the repository and clone your fork.
2. Edit the relevant Markdown or SVG files directly. There is no build step and no environment to set up.
3. If your change touches content that exists in both languages, update both, or say clearly in your pull request which language still needs it.

## Commit and pull request guidelines

- Use clear, descriptive commit messages (for example, `fix: correct broken link in installation guide`, not `update stuff`).
- Keep pull requests focused on a single change where possible. Smaller pull requests are reviewed faster.
- Fill out the pull request template completely, including what you changed and why.
- Be explicit in your pull request description if any part of your contribution was drafted with AI assistance. This project is itself built and documented as human-directed, AI-assisted work, so we ask for transparency about that, not avoidance of it.

## Reporting security or integrity issues

Please do **not** open a public issue for a security or integrity concern (a leaked secret in the history, a malicious link, content that reads as an operational guide to defeating a safeguard). See [`SECURITY.md`](SECURITY.md) for the private reporting process.

## Questions

Not sure where to start? Open an issue using the "Question" template. Beginner questions are explicitly welcome here.
